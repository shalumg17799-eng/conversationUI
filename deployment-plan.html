Azure Deployment Plan

Conversational UI — Generative BI Report Hub (React frontend + Node/Express backend + Google BigQuery)

Prepared 11 June 2026  •  Branch: vk4  •  Audience: deployment / engineering

Summary. The app is a static React frontend plus a lightweight Node/Express backend that proxies to Claude/Gemini and queries Google BigQuery. It is I/O-bound, not CPU-heavy. Recommended VM: Azure A2 v2 (2 vCPU, 4 GB RAM), or — better — Azure App Service (no VM to manage). The database (BigQuery) stays on Google and is reached over its API; no DB migration is required. The single most important code change is removing a hardcoded http://localhost:3001 backend URL in the frontend.

3. Code changes required (before deploy)

MUST 3.1 — Remove hardcoded backend URL in frontend

The streaming call points at localhost. In production this fails (browser tries to reach the user's own machine).

File: src/app/pages/Conversational_new.tsx — line ~2578 (and error text line ~2658).

// BEFORE — hardcoded, breaks in production
const res = await fetch("http://localhost:3001/api/conversational/stream", {

// AFTER — use env var, same pattern already used in BigQueryDashboard.tsx
const API_BASE = import.meta.env.VITE_API_URL || "http://localhost:3001";
const res = await fetch(`${API_BASE}/api/conversational/stream`, {

Then set VITE_API_URL=https://<your-backend>.azurewebsites.net at frontend build time. Note: src/app/components/BigQueryDashboard.tsx already does this correctly — copy that pattern.

SHOULD 3.2 — Lock down CORS on backend

Backend currently allows Access-Control-Allow-Origin: * (any site). For production, restrict to your frontend domain.

File: backend/src/index.ts — line ~16.

// Replace the wildcard "*" with your real frontend origin
const ALLOWED = process.env.FRONTEND_ORIGIN || "*";
res.header("Access-Control-Allow-Origin", ALLOWED);
// also update the same header inside the SSE res.writeHead(...) block (~line 33)

GOOD 3.3 — Confirm port + start command

Backend already reads process.env.PORT (good — Azure App Service injects its own PORT). Ensure start command is npm run build && npm start (runs tsc then node dist/index.js).

5. The database question (answered)

Stays on Google. No migration needed. BigQuery is serverless and API-only by design — even when the backend ran on Google it talked to BigQuery over the network. Moving the backend to Azure changes nothing except that you now authenticate with a service-account key (§4).
  • Adding more datasets later = just more queries. No effect on the Azure VM/app size — BigQuery does the heavy lifting on Google's side.
  • Watch cost: BigQuery bills per data scanned, plus small network egress for results leaving Google. Not the VM.
  • Only migrate if you later want everything in one cloud for latency/billing simplicity — optional, not required.

7. Step-by-step deployment

  1. Make code changes §3 (hardcoded URL → env var; lock CORS).
  2. Create GCP service account with BigQuery Data Viewer + Job User; download JSON.
  3. Backend → Azure App Service (Linux, Node 20). Set env vars §4. Deploy via GitHub Actions / Azure CLI / zip.
    • Enable WebSockets and ensure response buffering is off so the /stream SSE endpoint works.
    • Start command: npm run build && npm start in /backend.
  4. Frontend → Azure Static Web Apps. Set VITE_API_URL = backend URL. Build with vite build, serve /dist. SPA fallback to index.html (Static Web Apps does this automatically; the existing vercel.json rewrite is the equivalent).
  5. Set CORS: FRONTEND_ORIGIN on backend = the Static Web App URL.
  6. Smoke test: open the site, send a query, confirm streaming reply + a BigQuery-backed report render.
  7. Monitor: Azure metrics (CPU/RAM) + BigQuery cost dashboard. Resize VM/plan only if usage stays high.
